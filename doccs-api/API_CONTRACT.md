# Контракт с сервером kino.pub / kino.watch (по исходникам kpapp.link)

Источник: `app.js` в этой же директории — сохранённая копия `https://kpapp.link/js/app.min.js`
(минифицированный веб-клиент "KinoPub WebApp" для того же бэкенда, к которому уже ходит наш
Android TV клиент). Все выводы ниже проверены построчно по исходнику, а не по пересказу.

Более полная официальная спецификация того же API (на русском, под именем хоста
`api.service-kp.com`) уже лежит в репозитории: `docs/kinoapi.com/*.html`. Этот файл её не
дублирует, а фокусируется на том, что официальные доки не покрывают: реальный механизм выбора
хоста, точные поля ответов, которые реально читает чужой клиент, и эндпоинты/паттерны,
которых пока нет в Filmax.

Каждый эндпоинт помечен:
- ✅ **уже есть в Filmax** — не требует действий, разве что сверить поля.
- 🆕 **нет в Filmax** — кандидат на добавление.

## 1. Выбор хоста и отказоустойчивость (🆕 — самое ценное в этом разборе)

В Filmax сейчас один захардкоженный хост без фолбэка:
`core/network/src/commonMain/kotlin/com/filmax/core/network/HttpClientFactory.kt:26`
`const val BASE_URL = "https://smarttvcdn.online/"`.

kpapp.link устроен принципиально иначе — он **не доверяет одному хосту** и на старте
прогоняет health-check по списку зеркал:

```js
let API_LIST = ['https://api.boramoraboom.ru', 'https://api.srvkp.com'];
```

Алгоритм (`getConfig()` → `checkApiList()`, app.js:97-100):
1. Сначала грузится `GET /config.json` (относительно текущего домена) — оттуда приходит
   `CONFIG` (версия приложения, `default_settings`, `home_blocks`, `quality_list` и т.д.).
2. Для каждого хоста из `API_LIST` по очереди делается `GET {host}/v1/user` с таймаутом 5 секунд.
3. Хост считается рабочим, если ответ — **HTTP 401** с `responseJSON.status == '401'**
   (то есть эндпоинт существует и просто требует токен — это и есть health-check).
4. Первый ответивший 401 хост становится `APIA` (базовый хост), `API = APIA + '/v1'`.
5. Если ни один хост не ответил 401 — переключаемся на **прокси того же домена**:
   `API = '/api/v1'`, `APIA = '/api'` (т.е. свой сервер проксирует запросы к API — обходит
   блокировки на уровне DNS/IP клиента).
6. Отдельный, третий хост `APIS = 'https://api.ios-kp.store/api2/v1.1'` используется только
   для части запросов, помеченных флагом `apis=true` в обёртке запроса (см. ниже) — судя по
   всему, альтернативная версия API (`v1.1`), в этом файле реально используется для
   `GET /items/{id}` (короткий повторный запрос за `age_rating`, см. §4.1) и
   `GET /items/collections/{id}`.
7. Есть также `PROXY.cdn = 'https://m.staticpop.net'` — при `PROXY.use_cdn=1` (включено по
   умолчанию) все URL постеров/превью переписываются на этот хост через
   `CDN(link) = link.replace(/^https?:\/\/([^\/]+)/, PROXY.cdn)` (app.js:210). Аналогично есть
   `PROXY.hls` для проксирования плейлистов, если `PROXY.use_hls=1`.
8. Ручной режим `?proxy=1` в URL (`GlobalProxy`) сразу форсирует прокси-режим для всех
   четырёх видов трафика (api/apis/hls/cdn), минуя health-check.

Итог: у эталонного клиента есть 4 независимых уровня резервирования (API-хост, API2-хост,
HLS-прокси, CDN-прокси изображений), у Filmax — ноль. Это единственный раздел данного разбора,
где различие системное, а не «пара мелких полей».

## 2. Аутентификация (Device Flow)

Тот же OAuth2 Device Flow, что и в `docs/kinoapi.com/authentication.html`, и то же, что уже
реализовано в Filmax (`core/network/.../OAuth.kt`), но с **другими учётными данными клиента**
(это креды web-клиента kpapp.link, не наши — просто для справки, использовать их незачем):

```
client_id=xbmc
client_secret=cgg3gtifu46urtfp2zp1nqtba0k2ezxh
```

- `POST {APIA}/oauth2/device?grant_type=device_code&client_id=xbmc&client_secret=...`
  → `{code, user_code, verification_uri, expires_in, interval}`.
- Поллинг `POST {APIA}/oauth2/device?grant_type=device_token&client_id=...&code=...` — **не по
  таймеру**, а условием `expires_in % interval === 0` внутри общего секундного тикера обратного
  отсчёта (fail-safe от рассинхронизации: даже если вкладка "спала", следующий тик поймает
  ближайшее кратное `interval`).
- Успешный ответ `{access_token, refresh_token, expires_in}` → сохраняется в `localStorage`
  (`access_token`, `refresh_token`, `activation_time`, `expires_in`).
  **Refresh-логики в этом клиенте нет вообще** — токен не обновляется по `refresh_token`
  проактивно; при 401 просто заново запускается `getAccess()` (полный device-flow заново). Это
  слабее, чем у Filmax (там уже есть авто-refresh) — тут для нас урока нет, наша реализация лучше.
- Сразу после активации отправляется `POST /device/notify` с `{title: "KinoPub WebApp", hardware, software}`
  — `hardware`/`software` собираются из `$.ua` (User-Agent parser): `hardware = vendor + model + browser.name + browser.version`,
  `software = os.name + os.version`.
- Токен передаётся **query-параметром** `access_token=...` на каждый запрос, не заголовком
  `Authorization`. (Filmax использует Bearer-заголовок — это тоже расхождение, но не проблема:
  оба варианта поддерживаются бэкендом, у нас удобнее и безопаснее с точки зрения логов прокси.)

## 3. Обёртка запросов и кэширование (общий паттерн, не отдельный эндпоинт)

`getAPIdata(url, callback, noCache, apis, method, fields, processData)` (app.js:200-202):
- Собирает URL: `{API}{url}{?|&}access_token={token}`, либо `{APIS}{url}` если `apis=true`.
- Кэширует ответ в памяти (`CACHE`) на **3600 секунд** по ключу `url2name(url)` (транслитерация
  URL). GET без явного `noCache=true` может отдать данные часовой давности из кэша вместо сети.
- При `processData=false` тело уходит как `JSON.stringify(...)` с заголовком
  `content-type: application/json` (используется для `/device/{id}/settings`); во всех
  остальных POST — `application/x-www-form-urlencoded` через jQuery `data: fields`.
- Особая обработка ошибок: если `status == 401` и `url == '/user'` — считается, что устройство
  разлогинено, и автоматически перезапускается `getAccess()` (полная реактивация).

## 4. Каталог (items)

### 4.1 `GET /items/{id}?nolinks=0` ✅ (уже есть — `CatalogApi`/`ItemDto`)

Поля объекта `item`, которые реально читает клиент (сверх того, что уже есть в `ItemDto.kt`):

| Поле | Тип/пример | Уже в Filmax? | Комментарий |
|---|---|---|---|
| `title` | `"Rus Title / Original Title"` | частично | title_ru/title_en получаются **на клиенте** через `split(' / ')`, сервер отдаёт одну строку. У Filmax нет ни `title`, ни этого сплита — стоит проверить, не теряем ли оригинальное название. |
| `age_rating` | int, напр. `18` | 🆕 нет в `ItemDto` | возрастной рейтинг, показывается как `"{value}+"`; `-1`/отсутствие — не показывать. |
| `advert` | bool/флаг | 🆕 нет | показывает баннер "есть реклама в видео" |
| `views` | int | 🆕 нет (используется только `rating_percentage`) | форматируется `toLocaleString()` |
| `rating_votes`, `kinopoisk_votes`, `imdb_votes` | int | 🆕 нет | количество голосов к каждому рейтингу |
| `kinopoisk` | int (id) | 🆕 нет | id тайтла на Кинопоиске — ключ для `/kpapi/films/{id}/{type}` (см. §7); нам не нужен, т.к. используем TMDB |
| `bookmarks` | array | 🆕 нет | `bookmarks.length > 0` → тайтл лежит хоть в одной папке закладок текущего юзера |
| `quality` | int/код | 🆕 нет | ключ в `CONFIG.quality_list` (см. §8) — максимальное доступное качество тайтла целиком |
| `tracklist` | опционально | 🆕 нет | судя по всему, для концертов/музыкальных альбомов — трек-лист |
| `blocked_countries` | — | ✅ уже есть (`MovieInfoDto.blockedCountries`) | подтверждения в этом клиенте не нашлось (не факт, что вообще относится к `/items/{id}`, а не к другому эндпоинту) |

На каждый показ карточки тайтла клиент **дополнительно** делает три параллельных фоновых запроса
(если включено в настройках `SETTINGS.card.*`), которых у Filmax нет — см. §4.2.

Также интересно: сразу после основного запроса `/items/{id}` клиент **повторно** дёргает
`GET /items/{id}` через `apis=true` (то есть на альтернативный хост `APIS`, API v1.1) **только
чтобы прочитать `age_rating`** (app.js:168). Похоже, `age_rating` на момент написания клиента
не всегда был в основном API и появился раньше в v1.1 — сейчас, вероятно, уже не нужно
дублировать запрос, но сам факт показывает, что у бэкенда есть версия `v1.1` с более новыми
полями.

### 4.2 Похожие/по автору/по жанру/комментарии/вхождение в подборки — 🆕 нет в Filmax

Все четыре — GET-запросы, вызываются лениво (через 100-200мс после отрисовки карточки),
единообразно рендерятся в горизонтальный скроллер:

- `GET /items/similar?id={id}&perpage={n}` → `{items: [...]}` — «Похожие».
- `GET /items?director={первый_режиссёр}&sort=rating-&perpage={n}` → «Ещё у этого режиссёра».
- `GET /items?genre={id_первого_жанра}&sort=year-&perpage={n}` → «Ещё в этом жанре».
- `GET /items/collections/{id}` → `{items: [...]}` — подборки, в которые входит тайтл.
- `GET /items/vote?id={id}&like={0|1}` → `{voted: bool, positive: n, negative: n}` —
  лайк/дизлайк. `voted: false` означает "уже голосовали, повторно нельзя".
- `GET /items/comments?id={id}` → `{comments: [{user:{username,avatar}, message, rating,
  created (unixtime), depth}]}` — комментарии с вложенностью (`depth` = уровень отступа).

Всё это — маленькие, независимые, легко переносимые фичи для экрана деталей.

### 4.3 Списки/фильтрация ✅ (в целом уже есть в `CatalogRepositoryImpl`)

Подтверждённые параметры `GET /items`: `sort` (значения: `updated`, `created`, `popular`,
`fresh`, `hot`, `views`, `rating`, `kinopoisk_rating`, `imdb_rating`, с суффиксом `-` = DESC),
`genre` (id или список через запятую), `type` (список через запятую), `country`,
`finished` (0/1), `quality=4` (чекбокс "только 4K"), `perpage`, `page`, `director`,
`conditions[]` (массив строк вида `"year>=1990"`, `"kinopoisk_rating>=5"`, `"imdb_rating<=8"` —
собирается вручную и **не совпадает** по формату с одиночными `year`/`kinopoisk_rating`
из официальных доков — стоит свериться, если будем добавлять диапазонные фильтры).

Шорткаты `GET /items/{popular|fresh|hot}?type=&perpage=&page=` ✅ уже есть.

`GET /items/search` — два режима: с `field`/`type` (точный поиск) и упрощённый
`?q=...` при включённой опции "коррекция" (обычно опечаток) — не нашёл разницы в ответе,
похоже это один и тот же поисковый эндпоинт, просто с разным набором параметров.

## 5. Просмотры / прогресс (watching) ✅ почти всё уже есть

- `GET /watching/marktime?id={id}&time={sec}&video={n}&season={n?}` — вызывается **не по
  таймеру**, а на события плеера `seeked`, `pause`, `ended` (app.js:53, 180), и только если
  текущая секунда отличается от последней сохранённой (`marktime != last_time`). Это важно:
  не полить сервер запросами каждую секунду, а слать точечно на паузу/перемотку/конец. Стоит
  сверить, как это сделано в нашем плеере — если у нас интервальный поллинг, есть смысл перейти
  на событийную модель.
- `GET /watching/toggle?id=&video=&season=` ✅, `GET /watching/togglewatchlist?id=` ✅.
- `GET /watching/togglesubscribe?id=` — 🆕 в коде kpapp.link, но сам обработчик клика **обрезан
  `return!1` в самом начале функции** (app.js:34 — `return!1;let $btn=...`), то есть выключен
  на уровне frontend (мёртвый код/фича в разработке). Не приоритет.
- `GET /watching/{movies|serials}?subscribed={0|1}` ✅ — на «домашнем экране» используется
  специально: `subscribed=1` и `serials` вместе, чтобы посчитать счётчик новых серий
  (`item.new`) и подсветить пункт меню, если счётчик вырос с прошлого раза (сравнение через
  `localStorage.getItem('newEpisodes')`).

## 6. Устройства (device) — 🆕 настройки устройства нет в Filmax

- `GET /device/info` ✅ (частично) — дополнительно возвращает `device.settings`: словарь, где
  каждый ключ — либо чекбокс (`{value: bool}`), либо список (`{type:'list', value:[{id,label,
  selected}]}`). Это настройки плеера/приложения, которые сервер хранит **за устройство**
  (не за юзера) — например качество по умолчанию, автопереход к следующей серии и т.п.
  Конкретные ключи в этом файле не захардкожены (рендерятся динамически из ответа), так что
  набор ключей нужно смотреть по реальному ответу API, а не по этому JS.
- `POST /device/{id}/settings` — 🆕, тело `application/json`, объект вида
  `{...все ключи из device.settings с новыми значениями..., mixedPlaylist: 0, supportSsl: 1}`.
  Если решим показывать «настройки устройства» в Filmax (например синхронизировать качество/
  автопродолжение между устройствами одного аккаунта) — вот эндпоинт.
- `POST /device/notify` ✅ уже есть, тело `{title, hardware, software}` — отправляется и сразу
  после активации, и при каждом сохранении настроек устройства (обновляет "последний раз
  использовалось").

## 7. Сторонние источники (не наш backend)

- `GET /kpapi/films/{kinopoisk_id}/{type}` — прокси к Кинопоиску (актёры/похожее/т.п. — `{type}`
  берётся из `data-type` кнопки в UI). Не относится к нашему API-контракту: у Filmax уже есть
  TMDB для той же роли (см. `data/tmdb`), дублировать не нужно.
- `GET /users/{username}` — проверка, существует ли такой юзернейм на Кинопоиске (для какой-то
  "привязки" аккаунта); не относится к основному API, не приоритет.
- Спидтест: `https://speed.{msk|ams}-static-NN.cdntogo.net/speedtest/{garbage.php|empty.php}` —
  замер ping/скорости до CDN, используется только в разделе "Тест скорости" в настройках.
  Отдельная инфраструктура, не связанная с `api.*`.

## 8. Плеер: качество, звук, субтитры (ориентир для UX, не новый эндпоинт)

Все данные уже приходят в `/items/{id}` (файлы/аудио/субтитры — см. `MediaTrackDto` в
Filmax), новое здесь — как эталонный клиент их **использует**:

- **Список качеств** берётся не из ответа API, а из HLS-манифеста: после парсинга плейлиста
  через hls.js, `HLS.levels[]` даёт реальные уровни (ширина/высота/битрейт), и подпись строится
  через `CONFIG.quality_list[width]` (из `/config.json`) — то есть выбор качества полностью на
  стороне HLS-адаптивного стриминга, а поле `quality` из ответа `/items` используется только
  как текстовая подпись ("качество тайтла") на карточке, не для выбора потока.
- **Принудительные субтитры** определяются эвристикой по названию текстовой дорожки в самом
  видеофайле (`VIDEO.textTracks`), а не отдельным полем API: дорожка считается "форсированной",
  если её `label` начинается с `RUS` и содержит слово `Forced` (`label.indexOf('RUS')===0 &&
  label.indexOf('Forced')>0`, app.js:46). Это относится к встроенным HLS-сабтитрам (bundled в
  сам плейлист), не к отдельным `.vtt`/`.srt` из поля `subtitles` в ответе API — у нас это,
  скорее всего, два разных источника субтитров, стоит уточнить, какой использует Filmax.
- **Выбор аудиодорожки/субтитра по умолчанию для конкретной серии** запоминается в
  `localStorage` по ключу `i{item_id}` (аудио) и `t i{item_id}` (субтитры), а для сериалов —
  `i{item_id}s{season_number}` (то есть выбор помнится **на уровне сезона**, не серии и не
  тайтла целиком). Возможный UX-паттерн для Filmax, если сейчас выбор дорожки сбрасывается
  между сериями.
- Превью на таймлайне (тумбнейлы) собираются из `media.thumbnail`, куда клиент вручную
  подставляет секунду перемотки и суффикс размера в путь URL (`thumbnail[7] = time_ms;
  thumbnail[8] = '640.jpg'`, app.js:139) — то есть тумбнейлы лежат по URL-паттерну
  `.../{...}/{time_ms}/640.jpg` на CDN, а не отдаются готовым списком в API.

## 9. Рекомендации по улучшению Filmax (по приоритету)

1. **Резервные хосты API + health-check** (см. §1) — сейчас единственная точка отказа:
   если `smarttvcdn.online` заблокируют/ляжет, приложение не работает вообще. Стоит завести
   список из 2-3 хостов в `HttpClientFactory.kt`, проверку "первый ответивший 401 — рабочий",
   и падать на этот список при сетевой ошибке текущего хоста. Это единственный пункт здесь,
   который реально влияет на доступность приложения, а не только на набор фич.
2. **CDN-фолбэк для картинок** (§1, п.7) — если постеры/превью раздаются с отдельного
   медиа-хоста, есть смысл сделать то же самое: при ошибке загрузки картинки — попробовать
   переписать хост на запасной CDN, а не показывать плейсхолдер.
3. **`/items/similar`** — «Похожие» на экране деталей: маленький, самодостаточный, явно
   ценный для UX эндпоинт, один GET-запрос.
4. **`/items/vote`** — лайк/дизлайк тайтла на экране деталей: тоже маленький и самостоятельный.
5. **`age_rating`, `views`, `*_votes`, `advert`** в `ItemDto`/UI карточки — дешёвая добавка полей,
   если хочется показывать возрастной рейтинг и количество голосов рядом с рейтингом.
6. **Событийный, а не интервальный `marktime`** (§5) — если у нас сейчас прогресс шлётся по
   таймеру, переход на "шлём на seek/pause/ended, только если время изменилось" снизит нагрузку
   и трафик без потери точности резюме.
7. **Запоминание аудио/субтитров на уровне сезона** (§8) — небольшое, но заметное UX-улучшение,
   если сейчас выбор дорожки не сохраняется между сериями одного сезона.
8. **`/items/comments`, `/device/{id}/settings`** — низкий приоритет: комментарии и синхронизация
   настроек между устройствами — фичи, которые не являются ядром TV-плеера; добавлять только
   если появится явный запрос от пользователей.

Ничего из выше перечисленного не требует смены архитектуры — везде это либо новый метод в уже
существующем `*Api`/`*RepositoryImpl` (`CatalogApi`, `WatchingApi`), либо новое поле в уже
существующем DTO.
